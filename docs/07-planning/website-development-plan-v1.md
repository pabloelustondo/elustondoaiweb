## 1. Objective

Build a simple, professional, maintainable corporate website for Elustondo.ai, validate it through preview deployments and QA, and only then switch the elustondo.ai web DNS records from the current GoDaddy placeholder to Firebase Hosting.

## 2. Delivery model

The canonical implementation model is:
Specifications and reviewed content → AI-assisted coding → GitHub repository → automated checks → Firebase preview deployment → human QA → release approval → DNS cutover.

AI builders may accelerate design exploration or code generation, but GitHub remains the source of truth. No generated website is accepted directly into production without repository review, testing, and preview validation.

## 3. Initial technology stack

- React
- TypeScript
- Vite
- semantic HTML and restrained CSS/design tokens
- Firebase Hosting
- GitHub
- GitHub Actions for build, lint, and test checks

Avoid Next.js, Firestore, Authentication, Cloud Functions, and a CMS in v1 unless a concrete requirement appears.

## 4. V1 scope

Pages:
- Home
- Articles
- Projects
- Methods
- People
- About
- Contact

Core capabilities:
- responsive navigation;
- official brand assets;
- curated article links;
- selected project summaries;
- team/people presentation;
- direct contact path;
- metadata, favicon, Open Graph image, sitemap, and robots.txt;
- accessible and responsive layout;
- Firebase preview and production deployment configuration.

## 5. Content model

V1 content should live in typed local data files or structured TypeScript modules inside the repository. This keeps the site simple and reviewable.

Suggested content entities:
- ArticleSummary
- ProjectSummary
- PersonProfile
- MethodSummary
- ExternalLink
- SiteMetadata

A database or CMS should be introduced only when content update frequency and operational ownership justify the added complexity.

## 7. Branching and release practice

Use a simple model:
- main — releasable code;
- feature/* — bounded changes;
- optional release/* only when a release stabilization branch is justified.

Every meaningful change should be reviewable through a pull request or equivalent diff, even when generated by an AI coding agent.

## 8. Delivery phases

Phase 0 — Context and design
- confirm the website design specification;
- identify canonical logo files;
- inventory production content;
- mark all placeholders and uncertain claims;
- define page-level acceptance criteria.

Phase 1 — Repository and foundation
- create GitHub repository;
- scaffold React/TypeScript/Vite;
- configure linting, formatting, tests, and CI;
- add design tokens and official logo assets;
- configure Firebase Hosting for preview deployment.

Phase 2 — Homepage
- implement header and responsive navigation;
- implement hero;
- implement selected writing;
- implement current work;
- implement people section;
- implement secondary links/editorial note;
- implement footer;
- review desktop, tablet, and mobile layouts.

Phase 3 — Secondary pages
- Articles;
- Projects;
- Methods;
- People;
- About;
- Contact.

Phase 4 — Production hardening
- replace placeholders;
- verify public claims and roles;
- optimize images;
- add metadata and social preview assets;
- add accessibility checks;
- add performance checks;
- review error states and broken links.

Phase 5 — Preview QA
- deploy to Firebase preview or temporary web.app URL;
- conduct browser and device testing;
- gather review comments;
- correct issues;
- repeat until release criteria pass.

Phase 6 — Release
- record release approval;
- capture existing GoDaddy DNS state;
- add the Firebase custom domain;
- update only Firebase-required web DNS records;
- preserve PurelyMail MX, SPF, DKIM, and DMARC records;
- verify HTTPS and both apex/www behaviour;
- verify email remains operational;
- retain rollback information.

## 9. QA gates

Functional:
- all navigation works;
- all links resolve correctly;
- contact path works;
- no placeholder controls remain;
- no console errors in supported browsers.

Content:
- company name is correct;
- team names and roles are approved;
- project descriptions are safe for public release;
- article links and titles are canonical;
- contact information is correct;
- no residential address or unnecessary personal information is exposed.

Visual:
- official logo is used correctly;
- layout is coherent at desktop, tablet, and 320-pixel mobile widths;
- no overflow, clipping, stretched images, or inconsistent spacing;
- cards and typography preserve hierarchy.

Accessibility:
- semantic headings;
- keyboard navigation;
- visible focus states;
- labelled controls;
- meaningful alt text;
- sufficient contrast;
- reduced-motion compatibility.

Performance:
- optimized images;
- minimal JavaScript;
- no unnecessary third-party scripts;
- acceptable Lighthouse results for performance, accessibility, best practices, and SEO.

Operational:
- CI passes;
- Firebase preview is reproducible;
- production deployment command is documented;
- DNS rollback steps are documented;
- email DNS records are explicitly protected.

## 10. DNS cutover policy

The public domain remains at GoDaddy until the release candidate is approved. Creating a Firebase project or deploying a preview does not authorize DNS changes.

At cutover:
- change only records identified by Firebase for web hosting;
- do not delete or edit PurelyMail mail records;
- do not cancel the GoDaddy domain registration;
- verify SSL provisioning;
- verify apex and www behaviour;
- verify email send/receive after the change.

## 11. Security and privacy

V1 should minimize attack surface:
- no authentication;
- no database;
- no server-side form unless required;
- no unnecessary analytics;
- no embedded secrets;
- no public source maps if they expose sensitive information;
- dependency updates reviewed before deployment.

If analytics is added, it must have a defined purpose, privacy treatment, and cookie implications.

## 12. Definition of done

V1 is done when:
- the approved design is implemented with official assets;
- all public content is reviewed;
- responsive, accessibility, functional, and performance QA pass;
- the Firebase preview is approved by Pablo;
- release and rollback steps are documented;
- DNS is switched successfully;
- HTTPS works;
- email remains operational;
- the release is tagged and recorded.
