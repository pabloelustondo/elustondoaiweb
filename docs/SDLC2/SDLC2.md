SDLC2 — The Canonical 12-Step Cycle
A canonical methodology for AI-assisted software engineering
Introduction
SDLC2 is a knowledge-centred, specification-driven, evidence-driven methodology for AI-assisted software engineering. Its twelve steps are deliberately recognizable: domain analysis, intent, modelling, benchmarks, proof of concept, design, architecture, planning, specification, implementation, review, operation, and learning are established engineering responsibilities. The central change is not the abandonment of the software development lifecycle, but the pervasive presence of people working with AI throughout it. AI assistance participates in analysis, modelling, specification, implementation, testing, review, documentation, and learning, while human responsibility remains essential for intent, judgment, authorization, accountability, and the interpretation of evidence.
This pervasive assistance changes the relationship between engineering knowledge and implementation. In many conventional organizations, durable project knowledge is fragmented across several information spaces: documentation in systems such as Confluence, work planning in systems such as Jira, decisions in email and chat, and code and tests in Git repositories. Senior developers and technical leads must reconstruct the effective specification by navigating these spaces, resolving contradictions, identifying the latest authoritative version, and carrying critical context into implementation. AI development agents make this separation more consequential because an agent cannot reliably act from context that is inaccessible, inconsistent, obsolete, or dispersed across tools.
SDLC2 therefore closes the gap between documentation and development by making the core engineering context a curated, version-controlled part of the project repository. The repository is not treated merely as a container for source code. It becomes the authoritative working body of intent, models, use cases, benchmarks, architectural decisions, plans, specifications, implementation guidance, tests, evidence, and code required by both people and AI agents. External systems and sources still exist and may remain necessary, but the core context needed to understand, implement, evaluate, and evolve the system is brought together, reviewed for contradictions and omissions, and maintained with the implementation.
The twelve steps do not describe a rigid waterfall. They describe a disciplined sequence of engineering questions that progressively reduces uncertainty, converts understanding into explicit artifacts, and then confronts those artifacts with operational reality. Teams may revisit earlier steps whenever new evidence invalidates an assumption, but each step retains a distinct responsibility. The purpose of the cycle is not to maximize documentation or delay implementation. It is to ensure that implementation follows understanding, that testing follows explicit success criteria, and that learning from real operation returns to the domain model.
1. Context and Domain Analysis
Understand the world before proposing the system. This step establishes the business, organizational, technical, and human context in which the solution must operate. It identifies stakeholders, domain language, existing processes, current systems, constraints, incentives, pain points, assumptions, and sources of evidence. Domain analysis is not merely requirements gathering: it develops a coherent model of the problem space and exposes misunderstandings before they become software. In Project VISTA, this meant understanding the real shelf-inspection workflow, the responsibilities of coordinators, key account managers, inspectors, and reviewers, the structure of stores and shelves, and the operational limitations of mobile work. The output should be shared understanding expressed through domain concepts, responsibilities, context diagrams, process descriptions, and explicit unresolved questions.
2. Intent
State why the initiative exists and what business outcome it is meant to produce. Intent translates contextual understanding into a clear purpose without prematurely prescribing a technical solution. It should identify the desired change, the people who benefit, the value expected, the decisions the system should improve, the boundaries of the current initiative, and what is deliberately outside scope. A strong intent statement is concise enough to guide decisions but specific enough to reject attractive distractions. It gives every later artifact a criterion of relevance: architecture, features, tests, and plans must contribute to the declared intent. When alternatives arise, the team can ask which option better serves the underlying purpose rather than which technology is more fashionable.
3. System Model and Use Cases
Describe the system that must exist from the perspective of actors, responsibilities, information, and observable behaviour. The system model establishes boundaries: what belongs inside the system, what remains outside, which actors interact with it, and how information flows across those boundaries. Use cases then describe meaningful goals and scenarios rather than isolated screens or functions. Together, they convert broad intent into an actionable behavioural model while remaining independent of implementation technology. This step should capture primary and alternate flows, responsibilities, domain objects, important states, external systems, and failure conditions. In SDLC2, use cases are not lightweight decorations added after design; they are central instruments for reasoning about what the system must enable before deciding how it will be built.
4. Benchmarks, Test Strategy, and Success Criteria
Decide in advance how the team will know whether the solution is useful, correct, and better than the available alternatives. Benchmarks establish a baseline and a basis for comparison, which may include the current manual process, an existing system, a simpler technical approach, or no intervention at all. The test strategy identifies the kinds of evidence needed at each level, including unit, component, integration, system, usability, performance, security, field, and operational testing where relevant. Success criteria make expected outcomes explicit and measurable, while also acknowledging tolerances, uncertainty, and unacceptable failure modes. This step prevents the project from redefining success after implementation and makes testability a design concern from the beginning. It answers not only “Can we build it?” but also “What evidence would justify believing that it works?”
5. Viable Proof of Concept
Build the smallest credible experiment capable of resolving the most important uncertainty. A viable proof of concept is not a miniature product, an informal code dump, or an excuse to bypass engineering discipline. It is a deliberately bounded investigation with a hypothesis, a target question, representative inputs, observable results, and a clear decision that the evidence will inform. The experiment may validate technical feasibility, user interaction, data quality, performance, integration, or an architectural assumption. Its scope should be narrow enough to discard without regret and realistic enough to reveal meaningful constraints. The word viable emphasizes that the proof must be capable of answering the question; the word proof emphasizes evidence; and the word concept keeps it separate from production implementation.
6. Solution Design and Architecture
Shape the solution and allocate its responsibilities. Solution design addresses how users, information, workflows, and system behaviour should fit together; architecture establishes the structural and technical decisions that allow those behaviours to be delivered sustainably. Although design and architecture are distinguishable, they strongly constrain one another and therefore belong in the same stage of the canonical cycle. This step covers user experience, interaction flows, information models, component boundaries, responsibilities, interfaces, data movement, deployment structure, technology choices, architectural characteristics, and major trade-offs. Decisions should preserve their rationale, not merely their outcome, because architecture is context-dependent and evolves. The result should be a coherent solution whose parts have explicit responsibilities and whose structure supports the success criteria defined earlier.
7. Planning
Convert the designed solution into an executable sequence of work. Planning is deliberately separate from architecture because deciding what the system should be is not the same as deciding how a team will deliver it. This step decomposes the work into increments, milestones, workstreams, sprints, or other bounded units; identifies dependencies, risks, owners, decision points, and required evidence; and establishes an order that reduces uncertainty and enables early validation. Good planning avoids both speculative detail and vague aspiration. It should make the next meaningful action clear while preserving the ability to adapt when evidence changes. In agent-assisted development, planning also defines which tasks can be delegated, what context each agent requires, what outputs are expected, and where human review or authorization remains mandatory.
8. Specifications as Code: AI Agent-Ready Specifications
Consolidate the engineering knowledge produced by the preceding steps into an authoritative, repository-resident body of implementation context. This is the missing link between a conventional software development lifecycle and AI-assisted development. The earlier steps already produce specifications in a broad sense: intent specifies purpose, use cases specify behaviour, benchmarks specify evidence, architecture specifies structure, and planning specifies execution. Step 8 changes the status of that accumulated knowledge. It is curated, reconciled, version-controlled, traceable, and organized so that it can directly guide implementation and evaluation.
SDLC2 calls this Specifications as Code by analogy with Infrastructure as Code. The term does not mean that every specification must be written in a programming language or converted into executable syntax. It means that specifications are treated with the same engineering discipline normally reserved for source code: they live with the project, evolve through version control, are reviewed, compared, corrected, and kept aligned with implementation and tests. Contradictions, obsolete assumptions, missing decisions, ambiguous responsibilities, and competing versions are treated as engineering defects rather than as unavoidable documentation problems. Documentation review therefore becomes analogous to code review: another capable person or agent should be able to inspect the repository and determine whether the available context is coherent, sufficient, current, and authoritative.
The resulting specifications must be AI agent-ready. They define expected behaviour, interfaces, constraints, data structures, quality attributes, acceptance criteria, invariants, error handling, observability requirements, implementation boundaries, and the tests and evidence required for a bounded piece of work. They also preserve the rationale behind important decisions and identify unresolved questions or areas requiring human authorization. An AI development agent should not have to reconstruct the project from scattered Confluence pages, Jira tickets, email threads, meetings, and conversational memory before it can perform useful work. The core context required to understand the task should be available inside the repository, close to the code and tests it governs.
This does not imply that the repository contains every piece of organizational knowledge or replaces all external systems. Confluence, Jira, email, chat, external standards, and internet sources may continue to serve important purposes. The principle is narrower and more operational: the project repository must be sufficiently self-contained that a capable developer or AI agent can understand the current system, execute a bounded assignment, produce the required evidence, and determine whether the result conforms without depending on undocumented interpretation. In SDLC2, specifications are therefore behavioural source material and active engineering assets, not ceremonial documents.
9. Build and Test
Implement the specified capability and continuously collect evidence of conformance. Building and testing remain one integrated engineering responsibility because implementation without verification creates claims, while testing without reference to intent and specification produces activity without meaning. Work should proceed in bounded increments, with appropriate unit, component, integration, system, and exploratory tests executed as the capability grows. Tests should validate both expected behaviour and important failure modes, while code review, static analysis, instrumentation, and reproducible build evidence strengthen confidence. Passing tests are necessary but not sufficient: the team must confirm that the tested unit corresponds to a meaningful system responsibility and that mocked or isolated dependencies have not concealed integration failures.
10. Review and Release
Determine whether the increment is fit to leave the controlled development environment. Review evaluates correctness, architectural integrity, security, maintainability, usability, test evidence, documentation, operational readiness, and alignment with intent. Release is a governed decision, not simply the mechanical act of merging or deploying. The team should distinguish implementation claims from independently reviewed evidence, resolve material findings, record accepted risks, and verify rollback, support, configuration, migration, and communication needs where applicable. This step creates a clear quality gate: the question is not merely whether the software can be released, but whether it should be released given the available evidence and the consequences of failure.
11. Operational Reality
Place the integrated solution in the environment where real users, real data, real constraints, and real consequences determine its behaviour. Operational Reality replaces the narrower technical term runtime because the essential transition is not merely that a program is executing; it is that the engineered system has encountered the world it was designed to affect. Conditions are no longer selected entirely by the team. Lighting, networks, device limitations, workload, human behaviour, organizational incentives, unexpected inputs, and interactions among components may expose assumptions that controlled tests could not. This step distinguishes a system that builds, passes tests, or launches from a system that actually performs its intended responsibility in context. Operational Reality is where the solution becomes subject to reality rather than merely to its designers.
12. Observability, Insights, and Learning
Observe what the operating system and its surrounding environment reveal, convert evidence into insight, and feed that learning back into the next cycle. Observability includes the technical ability to understand internal state through logs, metrics, traces, events, diagnostics, and reproducible records, but the step is broader than instrumentation. It also includes user feedback, business outcomes, field observations, failure analysis, behavioural patterns, benchmark results, and discrepancies between intended and actual use. Evidence must be interpreted rather than merely collected: the team should identify what changed, why it matters, which assumptions were confirmed or rejected, and what decisions follow. The resulting learning updates Context and Domain Analysis, ensuring that SDLC2 remains an empirical cycle rather than a linear delivery process.
The Cycle as a Whole
The twelve steps form a progression from reality to intention, from intention to models, from models to evidence criteria, from uncertainty reduction to solution definition, from distributed engineering knowledge to AI agent-ready specifications, from specifications to implementation, and finally from controlled engineering into operational reality. The last step returns new knowledge to the first. This feedback is essential: SDLC2 treats code as an important but replaceable expression of understanding, while validated knowledge, decisions, responsibilities, specifications, and evidence form the durable engineering asset.
The methodology is intentionally evolutionary rather than revolutionary in its individual stages. Domain analysis, design, architecture, planning, implementation, testing, release, and learning are not new. What changes is the pervasive collaboration between people and AI agents and the closing of the historical gap between documentation and development. Specifications as Code places the authoritative engineering context in the same version-controlled environment as the implementation it governs. This enables people and AI agents to reason from a common body of knowledge, review documentation with engineering discipline, trace decisions into code and tests, and preserve what the project has learned.
In SDLC2, code is not the primary engineering artifact. The primary engineering artifact is the evolving body of validated knowledge from which code is produced, evaluated, operated, and regenerated. The repository therefore contains more than code: it contains the knowledge required to understand, implement, review, validate, maintain, and evolve the system. The canonical names may continue to improve as the methodology is exercised, but each responsibility should remain explicit so that teams do not confuse purpose with requirements, architecture with planning, documentation with authoritative specification, tests with operational truth, or release with learning.
